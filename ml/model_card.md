# Fino credit risk model — model card

Follows the hackathon's own model card template (`handouts/Handout_Checklist_and_Model_Card.pdf`).

| Section | Our answer |
|---|---|
| **Purpose** | Estimates the probability a loan applicant defaults within 12 months, to support Fino's `check_loan_approval` chat tool. Drafts an approve / manual-review / decline suggestion for the user to see — never a real bank decision. |
| **Data** | 6,000 synthetic Mtsvane Bank applicants (`credit_applicants.csv`, fictional, course-provided), 11.70% default rate. `applicant_id` and `collection_calls_after_loan` (leakage — only known *after* the loan is issued) excluded from features. `gender` excluded from features, kept only for the fairness check. Known gaps: no real Georgian credit bureau or repayment data; synthetic only. |
| **Method** | Tried a depth-3 decision tree (baseline-interpretable), logistic regression, and gradient boosting (`HistGradientBoostingClassifier`) — same split and hyperparameters as the course's reference notebook (NB1), so results are directly comparable. **Logistic regression is what runs live** in the chat tool: zero ML runtime needed in the Deno edge function, and every reason code is just `coefficient × value` — fully arithmetic, nothing the LLM has to infer. Gradient boosting is reported here as the stronger offline benchmark but is not deployed, to avoid adding a live-demo failure mode. |
| **Performance** | Held-out test set (30%, stratified, n=1,800). Baseline (predict the base rate): AUC 0.500. **Logistic regression (production): AUC 0.780, Gini 0.560.** Gradient boosting (offline only): AUC 0.800, Gini 0.601. Neither model exceeds 0.95 AUC, which would itself be a leakage red flag. |
| **Fairness** | Gender was never a model feature. Comparing the production model's outcomes by gender on the test set: approval rate 67.6% (women) vs. 69.5% (men) at the policy's 12%-PD cut-off; real default rate 12.4% (women) vs. 11.0% (men). Both pairs are close — no large disparity, despite gender being entirely unseen by the model. |
| **Limits** | Synthetic data only — not validated against real Georgian applicants or real bureau data. Not built for business/SME loans, mortgages, or applicants whose income currency differs from the loan currency (the policy treats those separately). Output is an estimate, always labeled as such in the chat response — never presented as a bank's real decision. |
| **Controls** | PTI (payment-to-income) rule applied **after** the model score, per `docs/01_consumer_loan_policy_en.md` §3: GEL loans ≤25% PTI if income <1,500 GEL else ≤50%; foreign-currency loans ≤20%/30% respectively. PD bands per policy §4: <6% auto-approve (if PTI also passes), 6–12% manual review, >12% decline. |
| **Owner & monitoring** | Hackathon prototype — no live monitoring yet. In production this would need a monthly check of default rates, approval-rate drift by group, and periodic retraining as the policy's income thresholds change (1,500 GEL → 2,000 GEL from Feb 2027 → 2,500 GEL from Sep 2027, per policy §3.4). |

## Responsible-AI checklist (hackathon's 5 questions)

1. **Explainability** — Yes. Every `check_loan_approval` response includes the top contributing factors (coefficient × value, sorted by magnitude) for that specific applicant, computed in code, not generated by the LLM.
2. **Fairness** — Yes, see Fairness row above. Region and employment type remain in the model as legitimate affordability signals; we did not test them individually as proxies for gender in this pass — noted as a follow-up, not yet done.
3. **Data privacy** — Training data is synthetic (course-provided), never leaves this repo's `ml/` folder, and is not sent to any external API. Live applicant inputs for the chat tool go only to the Gemini API for the model's own request (not the data file) and are not stored beyond the chat history already covered by Fino's existing Supabase setup.
4. **Model risk** — Honest held-out test (30%, stratified), a trivial baseline beaten by both real models, leakage column explicitly excluded (and the AUC-jump-to-leakage trap confirmed matches the course notebook's own finding), this model card, and a monitoring plan stated above (not yet implemented — hackathon prototype).
5. **Human oversight** — The tool only *drafts* a suggestion; it never auto-acts on the user's data. PD 6–12% is explicitly routed to "manual review" rather than an automatic decision, matching the bank policy itself.
